# Синхронизация Яндекс.Диска, которая не крутится весь день

> 🇬🇧 [English version](../yandex-sync.md)

К XPS 9500 это отношения не имеет — работает на любом Mac. Лежит здесь, потому что писалось на этой
машине и потому что интересна в нём не функция, а ограничение, верное для любого ноутбука:
**клиенту синхронизации нечего жечь батарею, пока им не пользуются.**

Официальный клиент Яндекс.Диска держит резидентный демон и опрашивает диск. Здесь та же работа делается
двумя файлами на Python и одним на Swift, а в простое приложение спит.

| | |
|---|---|
| [`tools/yandex-sync/yasync.py`](../../tools/yandex-sync/yasync.py) | Движок: конфигурация, синхронизация, поиск конфликтов, снимки общего предка |
| [`tools/yandex-sync/yadiff.py`](../../tools/yandex-sync/yadiff.py) | Трёхпанельное слияние в браузере, как в IDE |
| [`tools/yandex-sync/YandexSync.swift`](../../tools/yandex-sync/YandexSync.swift) | Приложение в строке меню: выбор папок, состояние и решение, *когда* синхронизировать |

Зависимости: `rclone` (один статический бинарник) и сама macOS. Python — только стандартная библиотека,
никакого `pip` и виртуальных окружений. Swift — один файл, собирается Command Line Tools.

---

## Установка

```bash
# rclone, если его ещё нет
mkdir -p ~/bin && curl -fsSL https://downloads.rclone.org/rclone-current-osx-amd64.zip -o /tmp/rc.zip
unzip -jo /tmp/rc.zip '*/rclone' -d ~/bin && chmod +x ~/bin/rclone

# авторизация — откроется браузер, токен останется в ~/.config/rclone/rclone.conf
~/bin/rclone config create yandex yandex

cp tools/yandex-sync/yasync.py tools/yandex-sync/yadiff.py ~/bin/
chmod +x ~/bin/yasync.py
~/bin/yasync.py init

swiftc -O tools/yandex-sync/YandexSync.swift -o ~/bin/YandexSync
~/bin/YandexSync &
```

Дальше папки выбираются через значок в строке меню, а «Запускать при входе» ставит агент launchd.

Токен OAuth лежит в конфиге rclone, и ничего из написанного здесь его не читает, не копирует и не пишет
в журнал.

## Когда запускается — и почему список такой короткий

Ни таймеров, ни циклов опроса. Приложение спит, пока его не разбудит ядро, и таких поводов ровно четыре:

| Событие | Чем ловится | Зачем |
|---|---|---|
| Файл изменился локально | `FSEventStream` на `~/YandexDisk`, коалесценция 2 с в ядре + задержка 10 с | Push из ядра. Пачка сохранений стоит ровно одной синхронизации |
| Стал активен Finder | `NSWorkspace.didActivateApplicationNotification`, не чаще раза в 2 минуты | Ближайшее к «пользователь открыл папку», что вообще есть в macOS |
| Пробуждение из сна | `NSWorkspace.didWakeNotification` | Пока крышка была закрыта, на сервере всё поменялось |
| Вернулась сеть | `NWPathMonitor`, только если она пропадала | Повторить то, что не удалось офлайн — один раз и ровно тогда, когда получится |

**Отдельного события «папку открыли» в macOS не существует.** Публичного API нет, Finder ничего не
рассылает. Кто говорит обратное — описывает либо цикл опроса, либо AppleScript, спрашивающий у Finder
его переднее окно. Активация Finder — честное приближение, поэтому она и придушена тайм-аутом.

Стоимость простоя — стоимость простаивающего `NSStatusItem`: ни таймеров, ни пробуждений, ни процессора.

## Сама синхронизация: `rclone bisync`

Двусторонняя синхронизация — решённая задача, и переписывать её плохо незачем. `rclone bisync` находит
изменения с обеих сторон, включая удаления и конфликты, и держит своё состояние в рабочем каталоге.

Важные ключи:

```
--conflict-resolve none        # никогда не выбирать победителя за пользователя
--conflict-loser pathname      # оставить ОБЕ версии, переименовав
--conflict-suffix local,remote # → doc.txt.local и doc.txt.remote
--resilient --recover          # переживать мелкие обрывы без полного resync
```

`--conflict-resolve none` вместе с `--conflict-loser pathname` — вся основа слияния: когда изменились
обе стороны, rclone кладёт рядом `doc.txt.local` и `doc.txt.remote`, и это вход для диффа.

### Страховку никогда не обходим молча

`bisync` отказывается продолжать, если разом изменилась подозрительно большая доля файлов — так обычно
выглядит случайно перемещённая или очищенная папка, а не работа. `yasync.py` ловит эту остановку,
записывает `lastResult: needs-confirm` вместе с причиной и останавливается. В меню появляется
**Подтвердить массовое изменение…** — оно показывает, что именно сказал `bisync`, и только потом
добавляет `--force`.

Автоматический `--force` сделал бы инструмент удобным и изредка катастрофическим.

## Конфликты: настоящее трёхстороннее слияние

Конфликт открывается из меню: локальный HTTP-сервер на `127.0.0.1` (случайный порт) отдаёт страницу
слияния. **Слева Яндекс.Диск, справа этот Mac, посередине живой результат.** Шевроны в жёлобах добавляют
сторону в результат. Нажали левое, потом правое — левое встанет над правым; наоборот — порядок
обратный. Порядок нажатий и есть порядок строк, поэтому отдельных кнопок «оба» не нужно.

Посимвольная подсветка внутри изменённых строк, линейка изменений у правого края, отмена и возврат на
каждый шаг, <kbd>F7</kbd> для перехода по различиям и ручная правка результата поверх.

### Почему двух версий мало и откуда берётся третья

Строка есть слева и нет справа — это либо *«слева добавили»*, либо *«справа удалили»*. Это разные факты,
и **дифф между двумя версиями их не различает.** Время файла тоже не помогает: у файла один `mtime` на
весь файл, по нему видно, какая версия сохранена позже, но никогда — какая *строка* правилась позже.
Построчной истории на диске нет нигде.

Разделить эти случаи может только третья версия — общий предок.

Поэтому `yasync.py` его хранит. После каждой удачной синхронизации, когда стороны сведены по
определению, он складывает снимок содержимого папки в `~/Library/Application Support/YandexSync/base/`:
gzip, инкрементально (файл перекопируется, только если изменились размер или mtime), всё крупнее 32 МБ
пропускается. Файлы, которые сейчас в конфликте, намеренно **не** переснимаются — их старый предок и
нужен слиянию.

С предком `build_blocks3` раскладывает каждый участок:

| Обе стороны относительно предка | Вывод |
|---|---|
| Изменилась только левая | Берём левую. Однозначно |
| Изменилась только правая | Берём правую. Однозначно — **включая удаления**, которые двусторонний дифф принял бы за добавление на другой стороне |
| Обе изменились одинаково | Это вообще не различие, не показывается |
| Обе изменились по-разному | Настоящий конфликт. Решает человек |

Однозначные участки проставлены сразу при открытии страницы, а кнопка **Слить неконфликтующие**
возвращает их после отмен. Настоящие конфликты автослияние не трогает никогда.

Если предка нет — файл появился уже в конфликте или он больше лимита — страница так и пишет, а
автослияние откатывается к единственному случаю, однозначному и без предка: односторонней вставке.
В строке состояния счёт честно помечен приблизительным.

### Офисные документы

`.docx`, `.doc`, `.rtf`, `.odt` разбираются через `textutil` — он встроен в macOS. `.xlsx` и `.pptx`
распаковываются как zip, XML читается стандартной библиотекой: таблицы превращаются в строки вида
`Лист!A1: значение`, презентации — в текст слайдов. То есть **видно**, что именно изменилось внутри
офисного документа.

Собрать `.docx` обратно из текста нельзя, поэтому для них слияние не поблочное, а целиком: выбрать
сторону. Страница об этом пишет, вместо того чтобы предлагать кнопки, которые породят битый документ.

`.xls` и `.ppt` (старые двоичные форматы) не читаются вообще.

## Файлы и состояние

| Путь | Что |
|---|---|
| `~/YandexDisk/` | Сами синхронизируемые папки |
| `~/Library/Application Support/YandexSync/config.json` | Какие папки, когда каждая синхронизировалась |
| `~/Library/Application Support/YandexSync/bisync/` | Состояние `rclone bisync` |
| `~/Library/Application Support/YandexSync/base/` | Сжатые снимки общего предка |
| `~/Library/Logs/yandex-sync.log` | Журнал |
| `~/.config/rclone/rclone.conf` | Токен OAuth — это rclone, не мы |

Движок работает и сам по себе:

```bash
yasync.py ls                  # папки на Диске
yasync.py add Документы       # взять под синхронизацию (первый раз — resync)
yasync.py sync --all
yasync.py status              # или state — то же в JSON
yasync.py conflicts
yasync.py resolve doc.txt     # откроет страницу слияния
```

## Честные ограничения

- **Предок появляется только после первой удачной синхронизации.** Конфликт, возникший раньше снимка,
  разбирается двусторонним запасным путём.
- **У файлов больше 32 МБ предка нет** и не будет — построчно их всё равно не сливают.
- **Правку, сделанную прямо во время синхронизации, наблюдатель может пропустить.** Он игнорирует
  события во время синхронизации и 5 секунд после, иначе наши собственные записи заводят его по кругу.
  Такая правка уедет не мгновенно, а при следующем событии.
- **Активация Finder — это приближение**, а не настоящий сигнал «папку открыли», см. выше.
- **Регистр имён и расширенные атрибуты** — забота `rclone`, а не наша; метки Finder и ресурсные вилки
  круговой рейс не переживают.
